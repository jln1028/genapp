## Customer Management Rules

### Customer Number Generation

**Rule CM-001: Dual Customer Number Strategy**
- **Location**: [`base/src/lgacdb01.cbl`](../base/src/lgacdb01.cbl:199-211)
- **Description**: The system supports two methods for generating unique customer numbers:
  1. **Named Counter Service (NCS)**: When available, uses CICS Named Counter `GENACUSTNUM` from pool `GENA`
  2. **Db2 Identity Column**: When NCS is unavailable, uses Db2's `IDENTITY_VAL_LOCAL()` function
- **Business Rationale**: Provides flexibility for different deployment scenarios and ensures unique customer identification across the sysplex
- **Implementation**: Flag `LGAC-NCS` determines which strategy to use

**Rule CM-002: Customer Number Tracking**
- **Location**: [`base/src/lgtestc1.cbl`](../base/src/lgtestc1.cbl:283-337)
- **Description**: Customer number ranges are tracked in temporary storage queue `GENACNTL`
- **Purpose**: Supports workload simulation and operational monitoring
- **Note**: This is not a best practice but provided for testing automation

### Customer Data Normalization

**Rule CM-003: Input Data Sanitization**
- **Location**: [`base/src/lgtestc1.cbl`](../base/src/lgtestc1.cbl:125-127)
- **Description**: Before adding or updating customers:
  - All low-values (x'00') are replaced with spaces (x'40')
  - Postcode is converted to uppercase using `UPPER-CASE` function
- **Business Rationale**: Ensures data consistency and prevents database issues with null characters
- **Applied To**: Customer add (option 2) and update (option 4) operations

**Rule CM-004: Customer Security Initialization**
- **Location**: [`base/src/lgacdb01.cbl`](../base/src/lgacdb01.cbl:179-189)
- **Description**: New customers receive default security credentials:
  - Password hash: `5732fec825535eeafb8fac50fee3a8aa`
  - Security count: `0000`
  - Security state: `N` (New)
- **Business Rationale**: Establishes baseline security posture for new accounts

### Customer Policy Count

**Rule CM-005: Policy Count Initialization**
- **Location**: [`base/src/lgacus01.cbl`](../base/src/lgacus01.cbl:103)
- **Description**: New customer records initialize `CA-NUM-POLICIES` to `00`
- **Business Rationale**: Provides baseline for tracking customer policy portfolio

## Policy Management Rules

### Policy Type Classification

**Rule PM-001: Policy Type Codes**
- **Location**: [`base/src/lgpolicy.cpy`](../base/src/lgpolicy.cpy:43), [`base/Architecture.md`](../base/Architecture.md:89-94)
- **Description**: Four policy types are supported:
  - `E` - Endowment insurance policy
  - `H` - House insurance policy
  - `M` - Motor insurance policy
  - `C` - Commercial property insurance policy
- **Business Rationale**: Categorizes insurance products for specialized processing and reporting

### Policy Number Generation

**Rule PM-002: Automatic Policy Number Assignment**
- **Location**: [`base/src/lgapdb01.cbl`](../base/src/lgapdb01.cbl:279-310)
- **Description**: Policy numbers are auto-generated by Db2 using `DEFAULT` value and retrieved via `IDENTITY_VAL_LOCAL()`
- **Business Rationale**: Ensures unique policy identification without manual intervention
- **Timestamp**: System automatically assigns `CURRENT TIMESTAMP` to `LASTCHANGED` field

### Policy-Customer Relationship

**Rule PM-003: Customer Existence Validation**
- **Location**: [`base/src/lgapdb01.cbl`](../base/src/lgapdb01.cbl:290-298)
- **Description**: Referential integrity enforced via Db2 foreign key constraint
  - SQLCODE `-530` indicates customer does not exist
  - Returns error code `70` to caller
- **Business Rationale**: Prevents orphaned policies and maintains data integrity
- **Error Message**: "Customer record must exist before policy creation"

### Policy Request Routing

**Rule PM-004: Request ID Validation**
- **Location**: [`base/src/lgapdb01.cbl`](../base/src/lgapdb01.cbl:184-207), [`base/src/lgupol01.cbl`](../base/src/lgupol01.cbl:113-141)
- **Description**: Request IDs determine policy operations:
  - `01AEND` - Add Endowment policy
  - `01AHOU` - Add House policy
  - `01AMOT` - Add Motor policy
  - `01ACOM` - Add Commercial policy
  - `01UEND` - Update Endowment policy
  - `01UHOU` - Update House policy
  - `01UMOT` - Update Motor policy
- **Invalid Request**: Returns error code `99`
- **Business Rationale**: Routes requests to appropriate policy-specific processing logic

### Policy Data Structures

**Rule PM-005: Variable-Length Endowment Data**
- **Location**: [`base/src/lgapdb01.cbl`](../base/src/lgapdb01.cbl:339-387)
- **Description**: Endowment policies support optional VARCHAR padding data
  - If commarea contains extra data beyond required length, it's stored in `PADDINGDATA`
  - Otherwise, `PADDINGDATA` field is omitted from INSERT
- **Business Rationale**: Accommodates flexible endowment policy structures

## Data Validation Rules

### Communication Area (COMMAREA) Validation

**Rule DV-001: COMMAREA Presence Check**
- **Location**: Multiple programs (e.g., [`lgacus01.cbl`](../base/src/lgacus01.cbl:95-99))
- **Description**: All business logic programs validate COMMAREA is received
  - If `EIBCALEN = 0`, program writes error message and issues ABEND with code `LGCA`
- **Business Rationale**: Prevents processing with missing input data
- **Error Message**: "NO COMMAREA RECEIVED"

**Rule DV-002: COMMAREA Length Validation**
- **Location**: Multiple programs (e.g., [`lgacus01.cbl`](../base/src/lgacus01.cbl:107-115))
- **Description**: Programs validate minimum COMMAREA length:
  - Customer operations: Header (18 bytes) + Customer data (72 bytes) = 90 bytes minimum
  - Policy operations: Header (28 bytes) + Policy-specific data
  - If insufficient, returns error code `98`
- **Business Rationale**: Prevents buffer overruns and ensures complete data transmission
- **Implementation**: Uses copybook-defined lengths from [`lgpolicy.cpy`](../base/src/lgpolicy.cpy:16-28)

### Return Code Standards

**Rule DV-003: Standard Return Codes**
- **Location**: [`bobz/DD.json`](../bobz/DD.json:126-137), multiple programs
- **Description**: Standardized return codes in `CA-RETURN-CODE`:
  - `00` - Success
  - `70` - Referential integrity violation (customer doesn't exist)
  - `90` - SQL/database error
  - `98` - Invalid COMMAREA length
  - `99` - Invalid request ID or unsupported operation
- **Business Rationale**: Provides consistent error signaling across application layers

## Transaction Processing Rules

### Two-Phase Commit Protocol

**Rule TP-001: Coordinated Db2 and VSAM Updates**
- **Location**: [`base/Architecture.md`](../base/Architecture.md:48-50)
- **Description**: Customer and policy additions use two-phase commit:
  1. Update Db2 database (customer/policy tables)
  2. Update VSAM file (KSDSCUST/KSDSPOLY)
  3. If VSAM update fails, Db2 update is rolled back
- **Business Rationale**: Maintains consistency between Db2 and VSAM data stores
- **Implementation**: CICS coordinates commit/rollback across resource managers
- **Note**: VSAM requirement is not best practice but demonstrates two-phase commit

**Rule TP-002: Rollback on Error**
- **Location**: [`base/src/lgtestc1.cbl`](../base/src/lgtestc1.cbl:132-135)
- **Description**: If customer add returns error code > 0:
  - Execute `SYNCPOINT ROLLBACK`
  - Display error message to user
- **Business Rationale**: Ensures atomic transactions and data consistency

### Transaction Layering

**Rule TP-003: Three-Tier Architecture**
- **Location**: [`base/Architecture.md`](../base/Architecture.md:30-38), [`AGENTS.md`](../AGENTS.md:18-20)
- **Description**: Strict program layering enforced:
  1. **Presentation Layer**: Programs like [`lgtestc1.cbl`](../base/src/lgtestc1.cbl) handle UI and user input
  2. **Business Logic Layer**: Programs like [`lgacus01.cbl`](../base/src/lgacus01.cbl) orchestrate operations
  3. **Data Access Layer**: Programs like [`lgacdb01.cbl`](../base/src/lgacdb01.cbl) and [`lgacvs01.cbl`](../base/src/lgacvs01.cbl) manage persistence
- **Communication**: Layers communicate via `EXEC CICS LINK` with COMMAREA
- **Business Rationale**: Separation of concerns enables componentization and maintainability

**Rule TP-004: COMMAREA as Contract**
- **Location**: [`AGENTS.md`](../AGENTS.md:21-22)
- **Description**: COMMAREA defined in [`lgcmarea.cpy`](../base/src/lgcmarea.cpy) is the stable interface contract
  - Request routing driven by `CA-REQUEST-ID` field
  - Callers may pass oversized lengths (e.g., 32500 bytes)
  - Interface changes must be copybook-first and cross-program
- **Business Rationale**: Maintains backward compatibility and loose coupling

## Error Handling Rules

### Error Logging

**Rule EH-001: Temporary Storage Queue Logging**
- **Location**: [`base/Architecture.md`](../base/Architecture.md:66-70)
- **Description**: Db2 errors are logged to temporary storage queue `GENAERRS`
  - Error messages include: date, time, program name, customer number, policy number, SQLCODE
  - Logging performed via [`lgstsq.cbl`](../base/src/lgstsq.cbl) program
- **Business Rationale**: Provides diagnostic trail for troubleshooting database issues
- **Note**: Using TSQ for error logging is not best practice but aids testing

**Rule EH-002: Error Message Format**
- **Location**: Multiple programs (e.g., [`lgacus01.cbl`](../base/src/lgacus01.cbl:39-48))
- **Description**: Standardized error message structure:
  - Date (8 bytes, MM/DD/YYYY format)
  - Time (6 bytes, HHMMSS format)
  - Program name (9 bytes)
  - Variable error details (21 bytes)
- **Business Rationale**: Consistent error reporting across application

**Rule EH-003: COMMAREA Error Logging**
- **Location**: Multiple programs (e.g., [`lgacus01.cbl`](../base/src/lgacus01.cbl:164-178))
- **Description**: On error, first 90 bytes of COMMAREA are logged to TSQ
  - Helps diagnose data-related issues
  - Truncates if COMMAREA < 90 bytes
- **Business Rationale**: Captures input context for error analysis

### ABEND Handling

**Rule EH-004: SQL Error ABEND**
- **Location**: [`base/src/lgapdb01.cbl`](../base/src/lgapdb01.cbl:389-394)
- **Description**: Critical SQL errors trigger ABEND with code `LGSQ`
  - Causes automatic rollback of Db2 updates
  - Issued with `NODUMP` option
- **Business Rationale**: Forces transaction backout to maintain data integrity

## Data Persistence Rules

### VSAM Key Structure

**Rule DP-001: Customer VSAM Key**
- **Location**: [`base/Architecture.md`](../base/Architecture.md:85-87)
- **Description**: KSDSCUST file key is first 10 characters (customer number)
- **Business Rationale**: Enables direct access to customer records by customer number

**Rule DP-002: Policy VSAM Key**
- **Location**: [`base/Architecture.md`](../base/Architecture.md:87-98)
- **Description**: KSDSPOLY file key is first 21 characters:
  - Position 1: Policy type code (C/E/H/M)
  - Positions 2-11: Customer number (10 digits)
  - Positions 12-21: Policy number (10 digits)
- **Example**: `M00000000050000000003` = Motor policy, customer 5, policy 3
- **Business Rationale**: Enables efficient retrieval by policy type and customer

### Database Referential Integrity

**Rule DP-003: Policy-Customer Foreign Key**
- **Location**: [`base/Architecture.md`](../base/Architecture.md:109-111)
- **Description**: Db2 enforces referential integrity:
  - Policy table has foreign key to Customer table
  - Cannot create policy if customer doesn't exist
  - Enforced at database level
- **Business Rationale**: Maintains data consistency and prevents orphaned records

**Rule DP-004: Timestamp Auditing**
- **Location**: [`base/src/lgapdb01.cbl`](../base/src/lgapdb01.cbl:284), [`base/src/lgapdb01.cbl`](../base/src/lgapdb01.cbl:316-321)
- **Description**: Policy records include `LASTCHANGED` timestamp
  - Automatically set to `CURRENT TIMESTAMP` on INSERT
  - Retrieved and returned to caller for audit trail
- **Business Rationale**: Provides change tracking for compliance and debugging

## Compliance and Audit Considerations

### Data Retention
- All customer and policy changes are timestamped
- Error logs maintained in temporary storage queues
- Transaction counts tracked via named counters (when configured)

### Referential Integrity
- Database-level foreign key constraints prevent orphaned policies
- Two-phase commit ensures Db2/VSAM consistency
- Rollback mechanisms protect against partial updates

### Security
- Customer passwords stored as hashes only
- Security state tracking for account lifecycle management
- Default security credentials established for new accounts
